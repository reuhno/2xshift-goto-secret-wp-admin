# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Ce que c'est

Extension Chrome **Manifest V3**, sans build, sans dépendance, sans tests. Nom public : « 2xShift Goto secret wp-admin ». Sur un site WordPress où l'on n'est pas connecté, un **double appui sur Shift (touche modificatrice configurable depuis 1.6.0, < 275 ms)** redirige vers l'URL de connexion cachée du site (règle mémorisée par hôte, ou proposition par défaut), avec `?redirect_to=` vers la page d'origine. Sur un site sans règle, un **overlay de première utilisation** propose de mémoriser l'accès.

## Dépôt git

- Remote `origin` : https://github.com/reuhno/2xshift-goto-secret-wp-admin.
- Une branche `feature/<slug>` par lot, fusionnée en avance rapide (fast-forward) dans `main`.
- `git push` réservé au propriétaire (Renaud) : un agent ne pousse pas de lui-même.
- `tools/` (comme tout dossier non chargé par Chrome) est à **exclure des zips envoyés aux stores** : seuls les fichiers réellement utilisés par l'extension (manifest, scripts, HTML, `_locales/`, `icons/`) doivent y figurer. Deux archives, deux manifestes : `dist/2xshift-<version>.zip` (Chrome Web Store, manifeste du dépôt tel quel) et `dist/2xshift-<version>-firefox.zip` (AMO, manifeste fusionné avec `tools/manifest-firefox.json`) — cf. section « Firefox ».

## Développement

- Chargée dans Chrome **directement depuis ce dossier** (« Charger l'extension non empaquetée », profil Default). Après toute modification : `chrome://extensions` → bouton ↻ de l'extension. Une page ouverte doit être rechargée pour recevoir le nouveau `content.js`.
- Journaux : sous l'option **Debug** de la page de réglages (case à cocher, `chrome.storage.sync.debug`). Rien ne s'écrit dans la console tant qu'elle n'est pas cochée. Le `console.log` de `content.js` est dans la console de la page ; celui de `background.js` dans « Inspecter les vues : service worker » sur `chrome://extensions`.
- Incrémenter `"version"` dans `manifest.json` à chaque modification livrée (SemVer, actuellement 1.6.0).
- Les libellés visibles passent par `_locales/{en,fr}/messages.json` (`__MSG_x__` dans le manifeste, `chrome.i18n.getMessage` dans `options.js`, `popup.js` et dans `content.js` pour l'overlay). Toute nouvelle chaîne s'ajoute **dans les deux langues**.
- Page de réglages en onglet plein : `manifest.json` déclare `options_ui: { page: "options.html", open_in_tab: true }` — écran « complet », conteneur centré `max-width: 760px`, cartes. Un clic sur l'icône de la barre d'outils ouvre le **popup** (`action.default_popup: "popup.html"`, écran « quotidien », 360 px de large) ; son lien « Tous les réglages » appelle `chrome.runtime.openOptionsPage()`. Plus de `chrome.action.onClicked` (incompatible avec un `default_popup`).
- `popup.html` / `popup.js` et `options.html` partagent l'habillage `ui.css` (variables de couleur, composants boutons/champs, mode sombre via `prefers-color-scheme`). Les deux pages protègent leurs appels `chrome.*` par `typeof chrome !== 'undefined' && chrome.storage` en tête de script, pour rester inspectables hors extension (ouverture `file://` ou serveur statique) : sans l'API, le HTML garde son balisage de secours (état représentatif, libellés en dur en français) et le script ne fait rien de plus.
- **Contraste (WCAG)** : cibles **4,5:1 pour tout texte** (y compris les liens) **/ 3:1 pour les bordures de contrôles, l'anneau de focus et les icônes**. Après toute modification des variables de couleur de `ui.css`, relancer `node tools/contraste.js` (mesure les paires texte/fond et bordure/fond des deux modes, clair et sombre) et corriger jusqu'à ce que tout passe.

## Modèle de stockage (`chrome.storage.sync`)

- `adminUrl` (chaîne) : **proposition par défaut**, peut être vide.
- `site:<hôte>` : une clé par site, `{ path: '/chemin/', redirectBack? }` ou `{ path: null }` (`null` = ne jamais rediriger sur ce site, la clé `redirectBack` n'a alors pas de sens et n'est pas écrite). Une clé par site plutôt qu'un tableau, à cause de la limite de 8 Ko par élément du stockage synchronisé. Hôte normalisé par `normalizeHost(url)` dans `background.js` (`new URL(url).hostname.toLowerCase()`, préfixe `www.` retiré) ; le content script reçoit toujours l'hôte déjà normalisé. `redirectBack` (booléen, **absent = suit le réglage global**) : surcharge par site de `redirectBack` ci-dessous ; une règle existante sans cette clé reste valide sans migration.
- `askOnNewSites` (booléen, **défaut `true` quand absent**) : à `false` et `adminUrl` non vide, un site sans règle est redirigé directement avec `adminUrl`, sans overlay.
- `redirectBack` (booléen, **défaut `true` quand absent** = comportement historique) : réglage global — ajouter `redirect_to` (retour sur la page d'origine après connexion) à l'URL de connexion. Valeur effective calculée par `resolveRedirectBack(stored, rule)` dans `background.js` : surcharge de la règle de site si booléenne, sinon ce réglage global si booléen, sinon `true`.
- `triggerKey` (chaîne) : réglage global, une des valeurs `event.key` `'Shift'`, `'Control'`, `'Alt'`, `'Meta'` — touche modificatrice à appuyer deux fois. **Absente ou valeur inconnue = `'Shift'`**, aucune migration. Pas de surcharge par site.
- `debug` : inchangé.
- **Migration** de l'ancien tableau `exceptions` `[{ url, adminUrl }]` : `migrateExceptionsIfNeeded()` dans `background.js`, appelée au début de `handleCheckCookiesAndRedirect` et dans `onInstalled` (toutes raisons). Idempotente : n'écrase jamais une clé `site:` déjà présente, supprime `exceptions` une fois traité.

## Architecture : détection paresseuse, overlay de première utilisation

1. **`content.js`** (toutes les URLs) — au chargement, ne fait **rien** d'autre qu'attacher l'écouteur `keydown` (gardes : `event.repeat`, champs de saisie / contentEditable, `overlayOpen`). Aucune lecture du DOM ni du stockage avant un appui sur une touche modificatrice. À chaque appui sur l'une des quatre (`MODIFIER_KEYS` : `Shift`, `Control`, `Alt`, `Meta` — sortie immédiate sinon) : timestamp et touche capturés **de façon synchrone** (`lastModifierPress`) avant d'attendre `readSettingsOnce()`, qui lit **en un seul appel** `chrome.storage.sync.get(['debug', 'triggerKey'])` (une fois par page, mis en cache) — ainsi le tout premier double appui de la page n'est pas raté à cause de la lecture asynchrone. Une fois la lecture résolue, si la touche pressée correspond à `triggerKey` et que l'appui précédent sur cette même touche date de moins de 275 ms, `handleDoubleShift()` s'exécute : mémo de page `pageKind` (null → évalué une fois par sélecteurs d'attributs uniquement — `link`/`script` pointant vers `/wp-content/`, `/wp-includes/`, `link[rel="https://api.w.org/"]`, `link[href*="/wp-json/"]`, meta `generator` — aucun `innerHTML`), puis mémorisé (`'wp'` ou `'other'`). Si `'wp'` et que l'utilisateur n'est **pas visiblement connecté** (`#wpadminbar` absent et pas de classe `logged-in` sur `<body>`), envoie `checkCookiesAndRedirect` au service worker. Le même listener `onMessage` traite aussi `getPageKind` ({} depuis le popup, via `background.js`) : réévalue/relit le même mémo `pageKind` et répond `{ pageKind, visiblyLoggedIn }` de façon synchrone — évalué seulement à la demande du popup (action de l'utilisateur), jamais au chargement.
2. **`background.js`** (service worker), sur `checkCookiesAndRedirect` ({ url }) : migration si besoin → `host = normalizeHost(url)` → une lecture `chrome.storage.sync.get(['adminUrl', 'askOnNewSites', 'debug', 'redirectBack', 'site:' + host])` → cookies `wordpress_logged_in*` classés par `classifyLoginCookies(cookies)` : `'valid'` → rien ; `'expired'` (log seulement) ou `'none'` → flux normal, comme s'il n'y avait pas de cookie. `parseLoginCookieExpiration(value)` décode la valeur du cookie (`decodeURIComponent` en try/catch), la découpe sur `|` (format WordPress `login|expiration|token|hmac`) et retourne le 2ᵉ champ en entier (secondes Unix) s'il est un entier positif, sinon `null`. `classifyLoginCookies(cookies)` ne garde que les cookies dont le nom commence par `wordpress_logged_in` : `'none'` s'il n'y en a aucun ; `'valid'` si au moins un a une expiration `null` (format inconnu → comportement historique prudent, on le garde pour valide) ou une expiration `* 1000 > Date.now()` ; `'expired'` sinon (tous périmés selon leur propre valeur). Puis, comme avant : règle de site présente : `path === null` → rien, sinon `redirectToAdmin()` ; pas de règle et `askOnNewSites === false` et `adminUrl` non vide → `redirectToAdmin()` direct ; sinon → `chrome.tabs.sendMessage(tabId, { action: 'askSiteRule', host, defaultPath, usualPath })`. `redirectToAdmin(url, path, tabId, redirectBack)` accepte un chemin ou une URL complète (n'en garde que le `pathname`), ne pose `redirect_to` que si `redirectBack` est vrai. La valeur effective de `redirectBack` est calculée par `resolveRedirectBack(stored, rule)` (surcharge de la règle de site > réglage global > `true`) — sauf pour le message `goToAdmin` du popup, qui la transmet déjà calculée (cf. point 5). Deux messages supplémentaires, envoyés par le popup pour son diagnostic (point 5), répondent via `sendResponse` et font `return true` dans le listener `onMessage` (réponse asynchrone) : `diagnoseSite` ({ url, tabId }) → `{ cookieStatus, pageKind, visiblyLoggedIn }` (`cookieStatus` par `getCookies(url)` + `classifyLoginCookies` ; `pageKind`/`visiblyLoggedIn` en interrogeant le content script de l'onglet via `chrome.tabs.sendMessage(tabId, { action: 'getPageKind' })`, forme callback — toute erreur ou absence de réponse donne `pageKind: 'unreachable'`, `visiblyLoggedIn: false`) ; `clearLoginCookies` ({ url }) → supprime, via `chrome.cookies.remove({ url: origin + cookie.path, name })`, tous les cookies dont le nom commence par `wordpress_logged_in` ou `wordpress_sec_` (le `path` du cookie est repris tel quel : `wordpress_sec_` est posé sur `/wp-admin` ou `/wp-content/plugins`, pas sur `/`), répond `{ removed: <nombre> }`.
3. **Overlay** (`content.js`, message `askSiteRule`) — n'existe pas avant le message. Un seul à la fois (`overlayOpen`). `<div>` hôte ajouté à `document.documentElement` (pas `body`), `attachShadow({ mode: 'closed' })`. **Jamais de `<style>` injectée directement** (CSP `style-src` de certains sites) : `new CSSStyleSheet()` + `replaceSync()` + `shadowRoot.adoptedStyleSheets`, repli sur une balise `<style>` dans le shadow si l'API est absente. `<form>` : Entrée valide, Échap et clic sur le voile annulent sans rien enregistrer et rendent le focus à `document.activeElement` d'avant ouverture. Choix : `/wp-admin/`, « choix habituel » (si `usualPath` défini et différent de `/wp-admin/`), chemin personnalisé (case cochée automatiquement à la saisie), ou « ne pas rediriger ». Validation → `chrome.runtime.sendMessage({ action: 'saveSiteRule', host, path, redirect })` ; c'est le service worker qui redirige, pas le content script.
4. **`options.html` / `options.js`** — quatre cartes dans l'ordre : Fonctionnement (texte d'explication), Réglages (`triggerKey`, `adminUrl`, `askOnNewSites`, `redirectBack`, `debug` dans un formulaire classique, bouton Enregistrer), Sites mémorisés, Crédits. Section « Sites mémorisés » : tableau construit depuis `chrome.storage.sync.get(null)` filtré sur les clés `site:`, écritures/suppressions **immédiates** (pas besoin d'Enregistrer). Colonne « Chemin d'admin » : champ texte plein largeur pour une règle avec chemin ; pour `path === null`, mention « Ne pas rediriger » + lien « Définir un chemin » qui la transforme en champ (annule si laissé vide). Colonne « Retour » : `<select>` à trois options (« Réglage global » valeur vide, « Oui », « Non ») qui écrit/efface `redirectBack` dans la règle du site, écriture immédiate comme le reste de la ligne ; désactivé (et remis sur « Réglage global ») quand `path === null`, la surcharge n'ayant alors pas de sens. Toute écriture du chemin (édition du champ) relit la valeur courante du select pour ne pas écraser une surcharge déjà enregistrée : `chrome.storage.sync.set` remplace tout l'objet de la règle, il n'y a pas de fusion partielle.
5. **`popup.html` / `popup.js`** — ouvert au clic sur l'icône, lit l'onglet actif (`chrome.tabs.query({ active: true, currentWindow: true })`, URL disponible via `activeTab` + `host_permissions`). Si l'URL n'est pas http(s) : seul le lien vers les réglages reste visible. Sinon : hôte normalisé, état de la règle, champ chemin pré-rempli (règle > proposition par défaut > `/wp-admin/`), `<select>` « Retour après connexion » (mêmes trois options que la colonne « Retour » d'`options.html`, désactivé et remis sur « Réglage global » quand la règle est `path === null`), bouton « Enregistrer pour ce site » (écrit `site:<hôte>` par lecture/écriture directe de `chrome.storage.sync`, comme `options.js` — le chemin et la surcharge `redirectBack` du select ensemble, y compris quand aucune règle n'existait encore), bouton « Y aller maintenant » (redirection immédiate **sans** enregistrer), liens « Ne pas rediriger sur ce site » / « Oublier ce site » (masqué si aucune règle). « Y aller maintenant » passe par un message `goToAdmin` ({ path, tabId, url, redirectBack }) au service worker plutôt que d'appeler `chrome.tabs.update` directement : depuis un popup, `sender.tab` est **absent** côté `background.js` (ce n'est pas un content script), d'où `tabId` et `url` transmis explicitement par le popup, qui les tient de `chrome.tabs.query`. `redirectBack` est calculé côté popup (select sur Oui/Non, sinon le réglage global déjà lu au dernier `refresh()`) et transmis déjà résolu plutôt que recalculé côté service worker : le popup reflète ainsi le choix affiché à l'écran même s'il diffère de ce qui est enregistré (bouton non encore cliqué) ; `background.js` retombe sur `true` si le message ne le transmet pas.
   - **Bloc diagnostic** (`#popup-diagnostic`, entre l'état de la règle et le champ chemin) — à chaque `refresh()` d'un onglet http(s), envoie `diagnoseSite` ({ url, tabId }) au service worker et affiche **un seul** cas, dans cet ordre de priorité : (1) `pageKind === 'unreachable'` (sauf si l'encart de permission Firefox est affiché : le content script n'est alors pas injecté et l'encart explique déjà la situation, le diagnostic reste caché) → apparence « warning » (même rendu que `.popup-permission-warning`, sélecteur CSS factorisé dans le `<style>` de `popup.html`), texte `popupDiagReload`, bouton `popupDiagReloadButton` qui recharge l'onglet (`chrome.tabs.reload`) puis ferme le popup ; (2) `pageKind === 'other'` → apparence discrète (« muted », pas de fond), texte `popupDiagNotWordPress`, pas de bouton ; (3) `cookieStatus === 'expired'` → « warning », texte `popupDiagExpiredCookie`, bouton `popupDiagClearCookiesButton` qui envoie `clearLoginCookies` ({ url }), affiche `popupDiagCookiesCleared` via `showStatus`, puis relance uniquement le diagnostic ; (4) `cookieStatus === 'valid'` ou `visiblyLoggedIn` → « muted », texte `popupDiagLoggedIn`, pas de bouton ; (5) sinon (ou toute erreur/absence de réponse) → bloc caché. Rien n'est affiché quand tout va bien : le bloc n'existe que pour signaler ce qui empêche le double appui de fonctionner sur l'onglet courant.

## Assistant d'installation

`onboarding.html` / `onboarding.js` — écran unique, ouvert par `background.js` **uniquement** sur `chrome.runtime.onInstalled` avec `details.reason === "install"` (même garde que l'ancienne ouverture de la page d'options : jamais à une mise à jour de Chrome ni à un rechargement d'extension non empaquetée). Relançable à tout moment depuis la carte « Fonctionnement » de `options.html` (lien « Relancer l'assistant », `chrome.tabs.create`) — préremplit alors le champ avec l'`adminUrl` existante plutôt que `/wp-admin/`. La validation normalise la saisie (trim, `/` initial garanti, URL complète réduite à son `pathname`, vide → `/wp-admin/`) et n'écrit que `adminUrl` ; la carte passe ensuite à un état « C'est prêt » sans rechargement de page. Habillage `ui.css` partagé (aucune variable de couleur propre à cette page), lien « Réglages avancés » vers `options.html` (`chrome.runtime.openOptionsPage()`).

Cookies `wordpress_logged_in*` conservés délibérément (décision du propriétaire) : en édition de texte on appuie souvent deux fois sur Shift par inadvertance, et sans cette vérification la redirection serait insupportable. Depuis 1.6.0, un cookie périmé selon sa propre valeur (date d'expiration inscrite par WordPress dans le cookie, dépassée) est ignoré : Chrome garde le cookie en stockage bien après cette date, ce qui sans cette classification laissait l'extension silencieuse alors que le site voyait l'utilisateur déconnecté (cf. `classifyLoginCookies`, point 2). Une révocation côté serveur avant cette date (déconnexion forcée, changement de mot de passe) reste indétectable sans requête réseau vers le site — choix assumé : l'extension ne fait aucune requête pour vérifier l'état de connexion, seul le diagnostic du popup (point 5) peut renseigner l'utilisateur, sur demande.

Pièges connus :
- `chrome.runtime.onInstalled` se déclenche à l'installation **mais aussi** à chaque mise à jour de Chrome et à chaque rechargement d'une extension non empaquetée : l'assistant d'installation (`onboarding.html`, depuis 1.4.0 — auparavant la page d'options) ne doit s'ouvrir que sur `details.reason === "install"` (garde introduit en 1.0.2, ne pas retirer). La migration `exceptions`, elle, tourne à chaque `onInstalled`, toutes raisons confondues. **Sur Firefox**, un module temporaire (chargé via `about:debugging` ou `web-ext run`) n'a pas d'identité persistante d'un rechargement à l'autre : `onInstalled` s'y déclenche avec `reason === "install"` à **chaque** rechargement, donc l'assistant se rouvre à chaque fois pendant les tests Firefox — c'est attendu, pas un bug.
- Le stockage est `chrome.storage.sync` : un profil sans synchro, ou un changement de profil, vide `adminUrl` et les `site:*`.
- `content.js` et `background.js` ont chacun leur propre assistant `log()` local (pas de fichier partagé) ; celui de `content.js` lit `debug` et `triggerKey` ensemble, en un seul appel, au premier appui sur une touche modificatrice, celui de `background.js` lit `debug` au même appel `chrome.storage.sync.get` que `adminUrl`. Même logique pour `normalizeHost()`/`normalizePath()` : dupliquées dans `background.js`, `options.js` **et** `popup.js` (pas de module partagé, convention du projet) — toute évolution de la normalisation se répercute dans les trois.
- L'overlay est dans un Shadow DOM **fermé** (`mode: 'closed'`) : inaccessible depuis la page hôte, y compris pour un script de la page qui tenterait de le lire.

## Firefox

Deux zips distincts depuis 1.5.0, un manifeste par navigateur : `manifest.json` (dans le dépôt) est un manifeste **pur Chrome**, chargeable non empaqueté sans aucun avertissement ; la variante Firefox est **générée à la fabrication**, jamais versionnée.

- **`manifest.json`** (dépôt, Chrome) : `background: { "service_worker": "background.js" }` seul. Pas de `browser_specific_settings`, pas de `background.scripts`.
- **`tools/manifest-firefox.json`** (généré nulle part, écrit à la main) : *uniquement* les clés à surcharger pour Firefox — `background.scripts` (Firefox ne supporte pas les service workers en arrière-plan ; `background.js` ne dépend d'aucune API propre aux workers : `self.`, `importScripts`, `clients`…) et `browser_specific_settings.gecko` (`id: "2xshift@reuhno.fr"`, obligatoire pour signer sur AMO ; `strict_min_version: "140.0"` ; `data_collection_permissions.required: ["none"]`, obligatoire pour toute nouvelle soumission AMO depuis Firefox 140 — d'où le `strict_min_version`, une version inférieure ne comprenant pas cette clé). JSON n'acceptant pas de commentaire, ce fichier n'en porte pas : sa raison d'être est documentée ici. `chrome.permissions` est une API ambiante : ne pas ajouter `"permissions"` à la liste `permissions` du manifeste, ce n'est pas une permission valide (`MANIFEST_PERMISSIONS` au lint).
- **Où modifier quoi** : une clé propre à Firefox (qui ne doit jamais atteindre Chrome) va dans `tools/manifest-firefox.json`. Tout le reste — permissions, content_scripts, icons, action, options_ui, version… — va dans `manifest.json` et se répercute automatiquement dans les deux archives.
- **Fabrication** : `./tools/build-zip.sh` produit `dist/2xshift-<version>.zip` (Chrome, fichiers du dépôt tels quels) **et** `dist/firefox/` + `dist/2xshift-<version>-firefox.zip` (Firefox). `dist/firefox/manifest.json` est le manifeste du dépôt **fusionné en python3** avec `tools/manifest-firefox.json` — fusion **peu profonde** : chaque clé de premier niveau des surcharges remplace celle du manifeste Chrome (donc `background` est remplacé en entier, sans `service_worker` ; `browser_specific_settings` est ajouté). Le dossier `dist/firefox/` est vidé puis reconstruit à chaque exécution ; l'archive Firefox est zippée depuis l'intérieur de ce dossier, pour que `manifest.json` soit à la racine de l'archive. Le script contrôle en plus que la version du manifeste Firefox généré est identique à celle du dépôt, qu'il ne contient pas `background.service_worker`, et qu'il n'a pas de clé de premier niveau absente du manifeste Chrome hormis `browser_specific_settings`.
- **Modèle de permission** : en MV3 Firefox, `host_permissions` (`<all_urls>`) et les `matches` des content scripts déclarés en **permissions requises** ne sont **pas** accordés d'office — sans l'accord de l'utilisateur, `content.js` ne s'injecte pas et le double Shift ne fait rien. Sur Chrome, ces mêmes permissions sont accordées à l'installation, sans dialogue.
- **Demande d'accès** : au submit de l'assistant de première installation (`onboarding.js`, fonction `requestAllUrlsPermission()`), avant d'enregistrer `adminUrl` — `chrome.permissions.request({ origins: ['<all_urls>'] })` (forme promesse `browser.*` avec repli callbacks `chrome.*` ; toute exception vaut accord, pour ne jamais bloquer Chrome). `adminUrl` est enregistrée dans tous les cas ; en cas de refus, l'état « C'est prêt » affiche un avertissement avec un bouton qui relance la demande. Filet de rattrapage dans le popup (`popup.js`) : au chargement, `chrome.permissions.contains({ origins: ['<all_urls>'] })` détermine si un encart d'avertissement (avec le même bouton) s'affiche au-dessus du contenu — n'apparaît jamais sur Chrome.
- **Lint** : `./tools/lint-firefox.sh` fabrique les archives (`build-zip.sh`) puis lance `web-ext lint --warnings-as-errors=false` directement sur `dist/firefox/` (plus besoin de décompresser). À relancer après toute modification du manifeste ou des scripts d'arrière-plan/permissions.
- **Tester manuellement** : `./tools/build-zip.sh` puis `npx web-ext run --source-dir dist/firefox` ouvre un profil Firefox de test avec l'extension déjà chargée (rechargement automatique sur modification de fichier — mais ces modifications ne portent que sur la copie dans `dist/firefox/`, pas sur les sources : relancer `build-zip.sh` après une modification du dépôt). Sinon, `about:debugging#/runtime/this-firefox` → « Charger un module temporaire » → sélectionner `dist/firefox/manifest.json` ; un rechargement manuel (bouton « Recharger ») est alors nécessaire après chaque `build-zip.sh`. Le popup et l'overlay demandent l'accès aux sites au premier lancement (assistant) ou depuis le popup — sans quoi le double Shift ne fait rien, cf. « Modèle de permission » ci-dessus.

## Jamais de vrai chemin d'admin dans le code

Les chemins secrets des sites du propriétaire ne doivent apparaître ni dans le code, ni dans les libellés, ni dans la doc, ni dans l'historique git (dépôt public). Exemple à utiliser partout : `/admin-securisee/`. Avant un commit, vérifier avec `git grep -i` que le vrai chemin du propriétaire (il le connaît, ne pas l'écrire ici) n'apparaît nulle part, y compris traduit en anglais dans `_locales/en`.
